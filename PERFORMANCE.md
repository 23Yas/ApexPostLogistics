# PERFORMANCE.md

## Environment and method

- Database: `ApexPostDb` on LocalDB, SQL Server 17.0.4025.
- Data: 50,200 `CounterTransactions` (200 seeded and 50,000 generated by `sql/15_generate_volume.sql`), 50,200 `Payments`, 50,200 `Shipments`, 100,400 `TransactionLines`, 50,200 `MoneyOrders` (generated by `sql/16_generate_money_orders.sql`), and 14 `BranchStock` rows.
- Method: `SET STATISTICS IO, TIME ON` with the actual execution plan on. Each workload was run twice and the second run is recorded. Reads are the reliable comparison. Elapsed time varies by a few milliseconds between runs.
- CPU time below 1 ms is shown as 0. This is SQL Server's timer resolution.
- Saved plans are in `docs\plans\`: `baseline-W1..W4.sqlplan`, `candidate-W2.sqlplan`, `sargable-W1-after.sqlplan`, `sargable-W2-after.sqlplan`, `sargable-W3-after.sqlplan`, `sargable-W4-after.sqlplan`.

## 2. Non-SARGable predicate: implicit conversion

The workload scripts compared `varchar` columns (`BranchCode`, `ServiceLevel`) with `N'...'` literals. SQL Server converts the column to `nvarchar` for each row, which can stop an index from being used to limit the read.

| Workload | Literal | Logical reads | CPU (ms) | Elapsed (ms) | Operator |
|---|---|---|---|---|---|
| W1 | `N'BR-001'` → `'BR-001'` | 30 → 10 | 0 → 0 | 15–18 → 20 | Index Scan |
| W3 | `N'Express'` → `'Express'` | 1434 → 1434 | 15–16 → 0 | 33 → 35 | Clustered Index Scan |
| W4 | `N'BR-002'` → `'BR-002'` | 1172 → 1172 | 32 → 15 | 95 → 98 | Index Scan |
| W2 (with candidate index, section 3) | `N'BR-001'` → `'BR-001'` | 322 → 67 | 31–32 → 0 | 38–40 → 21 | Index Scan, range-limited |

Conclusion: the literal change reduced reads for W1 and for W2 with the candidate index. It did not reduce reads for W3 or W4, because neither has an index that can seek on its filter columns. Those need indexes, not the literal change.

The EF application is not affected. The SQL log from the Daily report (section 6) shows EF sends branch codes as `AnsiString`, which matches the `varchar` columns.

## 3. Candidate index for W2

`IX_CounterTransactions_BranchCode_CreatedAtUtc_Covering` on `CounterTransactions (BranchCode, CreatedAtUtc) INCLUDE (Total)`. The key order puts the equality column first, then the range column. `INCLUDE (Total)` makes the index cover the query.

| Run | Literal | Logical reads | CPU (ms) | Elapsed (ms) |
|---|---|---|---|---|
| Baseline, no candidate | `N'BR-001'` | 1525 | 31–32 | 39–40 |
| Candidate present | `N'BR-001'` | 322 (the whole index) | 31 | 38–40 |
| Candidate present | `'BR-001'` | 67 | 0 | 21 |

- The index alone reduced reads from 1525 to 322. The `N'...'` literal meant the whole index was read.
- The literal change reduced reads further, from 322 to 67. That's about 21% of the index, consistent with BR-001 holding 10,040 of 50,200 rows (20%).
- Storage cost: 322 pages, about 2.5 MB (322 × 8 KB).
- Write overhead: **Not measured.** The script `sql/17_write_overhead.sql` is ready but hasn't been run.

**Decision: not adopted.** The index was dropped from the development database, so the schema matches the migrations. It is documented here as a measured candidate. Adopting it needs the write-overhead measurement, an EF configuration change, and a migration.

## 9. Known issues

- The stored procedures `usp_LowStockReport` and `usp_DailyBranchSales` take `nvarchar` parameters and compare them with `varchar` columns. This is the same implicit-conversion problem as section 2. It has not been fixed in the procedures.
- The measurements come from one machine and a single LocalDB instance, and most query times are in milliseconds. Use the reads as the reliable comparison.

## 10. Conclusions

1. The largest read reductions came from **matching literal types** (W1, W2) and from **a covering index on the equality and range columns** (W2). Both are measured.
2. W2's candidate index cut reads from 1525 to 67, but its write cost is unmeasured, so it is not adopted.
3. W3 and W4 are scans of their full tables. Candidate indexes are the expected fix. These are not measured yet and are listed as open items.
4. Parts of the evidence remain open: write overhead, the W3 and W4 candidates, estimated versus actual rows, the blocking observation, and the SQL samples.
